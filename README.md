# TRIDENT — NaiveProxy + mieru + VLESS

**[Установить на Ubuntu 24.04 одной командой](#quick-install)** · **[Обновить установленную панель](#update)** · [Открыть установщик](deploy/bootstrap.sh)

Самостоятельная панель для одного Linux VPS. Один человек получает три независимых доступа; порты закреплены за протоколами. Интерфейс на русском, backend на Node.js 24, база SQLite. npm-зависимостей нет.

<a id="quick-install"></a>

## Быстрый запуск одной командой — Ubuntu 24.04

На **чистом Ubuntu 24.04 VPS, x86_64/amd64, с systemd** выполните одну команду от пользователя с sudo (под root тоже работает):

```sh
sudo apt-get update && sudo apt-get install -y ca-certificates curl && (f=$(mktemp) && curl -fSL --retry 3 https://raw.githubusercontent.com/Gleb808/trident-panel/main/deploy/bootstrap.sh -o "$f" && sudo bash "$f"; r=$?; rm -f -- "$f"; exit "$r")
```

Команда сначала полностью скачивает установщик и только после успешной загрузки запускает его. Git и npm на VPS не требуются.

Установщик:

1. Проверяет Ubuntu, архитектуру, systemd, отсутствие прежней установки и свободный порт backend 8787.
2. Скачивает исходники `Gleb808/trident-panel` и официальные архивы **Node.js 24.21.0, Xray 26.3.27, mita 3.37.0, Caddy naive 2.11.2**.
3. Проверяет закреплённые SHA256 всех четырёх архивов перед распаковкой и запуском бинарников.
4. Устанавливает движки в `/usr/local/bin`, исходники в `/opt/trident-panel`, отдельный Node runtime в `/opt/trident-panel/runtime/node`.
5. Запускает backend панели и ждёт успешного ответа `/healthz`.

При успешном завершении откройте панель через SSH-туннель, создайте пароль администратора и настройте домен/порты по шагам ниже. Установщик выводит эти команды в терминал. Системный Node.js остаётся прежним; firewall и SSH-настройки не меняются. Агент и протоколы включаются после настройки панели.

**Windows:** [скачайте OPEN-PANEL.bat](https://raw.githubusercontent.com/Gleb808/trident-panel/main/OPEN-PANEL.bat) и запустите двойным щелчком после установки VPS. Введите IP/домен, SSH-логин и SSH-порт (по умолчанию `root` и `22`). Требуется встроенный OpenSSH Client Windows 10/11. Пароль запрашивает OpenSSH; батник его не сохраняет. После проверки `/healthz` браузер откроется автоматически. Держите окно BAT открытым: оно поддерживает туннель. Локально используется порт 18787 либо свободный порт, если этот занят; на VPS — 8787.

**ARM64 пока не поддерживается автоматической установкой:** у закреплённого выпуска Caddy naive нет готового ARM64-архива. Повторный запуск не перезаписывает панель, её данные или существующие движки. После прерванной установки сначала изучите сообщение об ошибке; это не автоматический механизм обновления или отката пакетов.

Исходник для просмотра: [`deploy/bootstrap.sh`](deploy/bootstrap.sh). SHA256 взяты из официальных GitHub Releases, для Node — из [выпуска 24.21.0](https://nodejs.org/en/blog/release/v24.21.0). Репозиторий загружается с текущего `main`; для воспроизводимой установки можно заранее скачать bootstrap и запустить `sudo env TRIDENT_REF=FULL_COMMIT_SHA bash bootstrap.sh`.

## Что готово

- Вход администратора, первичная настройка через localhost/SSH-туннель.
- Пользователи: создание, редактирование, поиск, фильтры, срок действия, отключение, удаление, продление на 30 дней.
- Независимые пароли NaiveProxy/mieru и UUID VLESS; перевыпуск комплекта и отзыв ссылки выдачи.
- ZIP с тремя ссылками импорта (`naive.txt`, `mieru.txt`, `vless.txt`), тремя нативными JSON и инструкцией. VLESS использует **XHTTP + REALITY**, без Vision flow.
- Персональная страница `/access#TOKEN`: выдаёт конфиги только для активного пользователя и после подтверждения актуальной конфигурации агентом.
- Серверные конфиги Caddy, mita, Xray, проверка конфликтов портов.
- Шифрование записей AES-256-GCM, scrypt для пароля администратора, HttpOnly/SameSite-cookie, проверка Origin/Host и CSRF, ограничение частоты входа.
- Linux-агент: снимок базы → проверка портов и версий → проверка конфигов → применение → проверка процессов/TCP-портов → откат при ошибке.
- systemd units, установочный скрипт, резервное копирование и тесты.

**Проверено на Ubuntu 24.04:** [полный CI прошёл](https://github.com/Gleb808/trident-panel/actions/runs/35231657688) — установка, обновление с сохранением пользователей и ключей, восемь тестов приложения, настоящий трафик NaiveProxy, mieru и VLESS XHTTP + REALITY, отказ старых ключей и IPv6 для VLESS. В тесте используется локальный TLS-сертификат; DNS, ACME, firewall и клиентское приложение на вашем VPS проверяются отдельно. Подробнее: [VALIDATION.md](VALIDATION.md).

## Локальный запуск

Требуется Node.js **24.x**. Из каталога проекта:

```sh
node src/server.mjs
```

Открыть **http://127.0.0.1:8787** и задать пароль администратора (минимум 12 символов). Первый запуск пустой: демонстрационные пользователи в поставку не включены. Установка npm-пакетов не нужна.

```sh
npm test
```

Для Windows без npm в PATH:

```powershell
node --test --test-isolation=none test/*.test.mjs
```

Переменные окружения: `DATA_DIR` (по умолчанию `data/` внутри проекта), `PORT` (8787), `AGENT_STATE` (путь к `state.json` агента). Backend всегда слушает **только 127.0.0.1**. Не публикуйте его HTTP-порт напрямую.

## Порты

| Назначение | По умолчанию |
|---|---|
| NaiveProxy | 443/TCP; опционально 443/UDP |
| VLESS + XHTTP + REALITY | 8443/TCP |
| mieru / mita | 20000–20009/TCP |
| Панель HTTPS | 9443/TCP |
| Caddy ACME | 80/TCP |
| Backend панели | 127.0.0.1:8787/TCP |
| Caddy admin | 127.0.0.1:2019/TCP |
| SSH | 22 зарезервирован, фактический SSH-порт нужно учитывать при установке |

Проверка намеренно строже уникальности сокетов: номер порта не используется разными протоколами даже на разных IP/TCP/UDP. При включении QUIC один и тот же NaiveProxy использует 443/TCP+UDP; эта же настройка включает HTTP/3 у HTTPS-панели (9443/UDP), но для браузерной панели достаточно TCP. Диапазон mieru ограничен 100 портами. На агенте `ss -ltnup` проверяет фактическую занятость, в том числе wildcard/IPv6 listeners. Процесс на занятом порту должен принадлежать соответствующему systemd unit.

Локальные SOCKS-порты в клиентских файлах тоже различаются: **1080 / 1081 / 1082**. У mieru RPC-порт 8964. Если эти номера заняты на устройстве пользователя, их нужно поменять в клиенте.

## Установка на VPS

### Ручная установка

Для отдельного Debian/Ubuntu VPS с systemd, доменом и публичным IPv4 можно подготовить зависимости самостоятельно. Существующую чужую панель установщик не заменяет. Для других дистрибутивов проверьте пути `/usr/bin/ss`, `/usr/bin/systemctl`.

### 1. Установить движки из официальных выпусков

Этот шаг нужен только при ручной установке; быстрый запуск выше выполняет его автоматически. Установите:

| Компонент | Целевая версия | Исполняемый файл |
|---|---|---|
| Node.js | 24.x | `node` в PATH либо `TRIDENT_NODE_BINARY` |
| Xray-core | 26.3.27 | `/usr/local/bin/xray` |
| mieru server / mita | 3.37.0 | `/usr/local/bin/mita` |
| Caddy + forwardproxy naive | 2.11.2-naive | `/usr/local/bin/caddy` |

Официальные источники:

- [Xray 26.3.27](https://github.com/XTLS/Xray-core/releases/tag/v26.3.27)
- [mieru/mita 3.37.0](https://github.com/enfein/mieru/releases/tag/v3.37.0)
- [Caddy forwardproxy naive 2.11.2](https://github.com/klzgrad/forwardproxy/releases/tag/v2.11.2-naive)
- [Node.js](https://nodejs.org/en/download)

Выберите сборку под архитектуру VPS, проверьте опубликованные контрольные суммы. Для mita предпочтителен tar.gz с бинарником: отдельный сервис из deb-пакета может занять порты. Не запускайте одновременно штатный `mita.service` и `trident-mita.service`.

Агент проверяет строку версии и наличие `http.handlers.forward_proxy`. Это **не** проверка происхождения модуля: именно сборку ветки naive необходимо получить из указанного источника. Версии зафиксированы по upstream releases, полученным при разработке; новые версии нужно отдельно проверять, а не подменять автоматически.

### 2. Установить панель

При ручной установке скопируйте проект на VPS, затем из его каталога:

```sh
sudo bash deploy/install.sh
```

Установщик создаст системных пользователей `trident` и `mita`, `/opt/trident-panel`, каталоги состояния и пять systemd units. Node копируется в `/opt/trident-panel/runtime/node`, который используют панель и агент. Если Node установлен вне PATH, передайте `sudo env TRIDENT_NODE_BINARY=/absolute/path/to/node bash deploy/install.sh`. Запустится только локальный backend панели. После быстрого запуска повторять этот шаг не нужно.

На своём компьютере:

```sh
ssh -L 8787:127.0.0.1:8787 your-user@your-server
```

Откройте `http://127.0.0.1:8787`, создайте пароль администратора и настройте:

1. Реальный домен сервера. A-запись должна вести на VPS. Не включайте обычный HTTP CDN-proxy поверх NaiveProxy/REALITY.
2. Email для сертификата.
3. Порты, не занятые другими сервисами.
4. REALITY SNI и порт целевого сайта. Значение `www.microsoft.com:443` — начальный шаблон; проверьте доступность, TLS 1.3 и подходящее поведение целевого сайта из сети VPS. Не направляйте REALITY обратно на свой прокси.

На firewall разрешите выбранные публичные порты, 80/TCP для ACME и существующий SSH-доступ. Для панели 9443/TCP можно использовать ограничение по IP, но тогда персональные страницы выдачи также будут доступны только этим IP. 8787 и 2019 наружу не открывать. Установщик firewall не меняет.

### 3. Запустить агент

```sh
sudo systemctl enable --now trident-agent
sudo journalctl -u trident-agent -u trident-caddy -u trident-mita -u trident-xray -n 100 --no-pager
```

Агент запускает движки сам. Не включайте их автозапуск отдельно: после перезагрузки агент должен сначала пересчитать истёкшие доступы и записать актуальный снимок.

Панель станет доступна по `https://YOUR_DOMAIN:9443`. Для смены домена/порта панели используйте SSH-туннель: старая публичная точка может стать недоступна в процессе изменения. При перезапуске Caddy ответ страницы иногда обрывается — заново откройте новую точку после применения.

### 4. Проверка реального подключения

В панели создать одного тестового пользователя. Дождаться сообщения о применении конфигурации. Скачать его ZIP и проверить **с внешнего устройства**:

```sh
# NaiveProxy client, отдельный терминал:
naive naive.json
# Проверка через локальный SOCKS5:
curl --socks5-hostname 127.0.0.1:1080 https://example.com

# mieru client:
mieru apply config mieru.json
mieru start
mieru test

# Xray client, отдельный терминал:
xray run -config vless.json
curl --socks5-hostname 127.0.0.1:1082 https://example.com
```

Проверьте отключение пользователя, истечение срока, перевыпуск ключей и перезагрузку VPS. Старый комплект должен перестать подключаться; новый — работать. Агент проверяет процессы и локальные TCP-listeners, но это не заменяет реальный протокольный handshake, проверку сертификата, firewall, маршрутизации и QUIC снаружи.

## Как применяется состояние

База — источник желаемого состояния. Агент каждые 30 секунд читает согласованный снимок, исключает истёкших/отключённых пользователей и вычисляет хеш серверных файлов. Изменение срока, переводящее пользователя в expired, меняет хеш даже без записи в базу.

1. Проверка домена, диапазонов портов, бинарников и их версий. При наличии пользователей — проверка цели REALITY: доверенный сертификат, TLS 1.3, HTTP/2 (h2), таймаут 8 секунд. Ошибка останавливает применение до изменения конфигов.
2. Проверка слушающих процессов через `ss` и MainPID systemd.
3. Запись candidate в root-owned каталог.
4. `caddy validate` и `xray run -test`. У mita нет отдельного standalone validate; ошибка загрузки выявляется при старте и проверке listener.
5. Замена конфигов и **полный перезапуск** трёх движков. Активные соединения прерываются, в том числе у остальных пользователей. Это осознанное ограничение v0.1.
6. Проверка процессов и всех ожидаемых TCP-портов; сохранение успешной ревизии.
7. При ошибке активации — восстановление предыдущих файлов и сервисов. При первом неудачном применении прежнего рабочего снимка нет: сервисы останавливаются, панель остаётся доступна через SSH-туннель.

Операция между тремя движками не атомарна. В процессе применения возможна краткая частичная доступность. Ошибка отображается в панели; повтор — в следующем цикле. Если откат вернул старую конфигурацию, старые доступы могут продолжить работать до успешного применения. При критическом отзыве проверяйте фактический результат; резервный вариант — остановить соответствующие units.

При пустом списке активных пользователей Xray и mita остановлены, Caddy обслуживает только страницу и панель. Не создаётся открытый NaiveProxy без пароля.

Сроки в формах — **включительно по UTC**. Фактическое отключение происходит после цикла агента и применения. Если агент выключен/ошибается, работающий движок сам не узнает об истечении срока.

## Хранение и резервная копия

Пользователи и настройки хранятся в `panel.sqlite`: значения `users.record` и `meta.value` зашифрованы AES-256-GCM. Это не полнодисковое шифрование SQLite: идентификаторы записей, журнал действий и таблица сессий остаются читаемыми. В журнале есть имена пользователей, но нет их протокольных паролей. `master.key` — отдельный локальный файл, необходимый для расшифровки. Это защита секретных записей при чтении одной только базы, не от компрометации сервера, где лежат оба файла.

```sh
# На локальной машине, из каталога проекта:
node scripts/backup.mjs /secure/path/trident-backup

# На VPS:
sudo -u trident env DATA_DIR=/var/lib/trident /opt/trident-panel/runtime/node /opt/trident-panel/scripts/backup.mjs /var/lib/trident/backup
```

Скрипт использует SQLite Backup API, поэтому корректно работает с WAL при запущенной панели. Копия содержит базу и master.key. Храните её вне VPS в защищённом месте; файлы вместе дают доступ к секретам.

Для восстановления остановите panel и agent, восстановите **согласованную пару** `panel.sqlite` + `master.key` в пустой каталог данных, назначьте владельца `trident:trident` и права 0600, запустите panel и agent. Не накладывайте файл БД поверх старого активного WAL. Caddy-сертификаты хранятся отдельно в `/var/lib/trident-caddy`.

Серверные конфиги, клиентские ZIP и `manifest.json` агента содержат секреты. Их нельзя коммитить или публиковать. В поставку проекта они не включены.

<a id="update"></a>

## Обновление установленной панели

На VPS с уже установленным TRIDENT:

```sh
(f=$(mktemp) && curl -fSL --retry 3 https://raw.githubusercontent.com/Gleb808/trident-panel/main/deploy/update.sh -o "$f" && sudo bash "$f"; r=$?; rm -f -- "$f"; exit "$r")
```

Обновитель скачивает исходники, проверяет синтаксис, останавливает panel/agent, сохраняет исходники, systemd units и согласованную копию базы с master.key в закрытом каталоге /var/backups/trident-update.*. Затем обновляет код и units, создаёт служебного пользователя mita и запускает панель. Ранее работающий агент возобновляется. При ошибке обновления исходники и units восстанавливаются; база и сертификаты остаются на месте. Путь резервной копии выводится в терминал. Движки и private Node runtime этим скриптом не обновляются.

**После перехода с v0.1.0 повторно скачайте VLESS-конфиг:** транспорт изменён с RAW/Vision на XHTTP + REALITY; flow должен быть пустым. UUID, REALITY-ключи, пароли NaiveProxy/mieru и пользователи сохраняются. Старые настройки получают путь XHTTP /trident.

Если агент ещё не включён, после настройки домена выполните:

```sh
sudo systemctl enable --now trident-agent
```

Дождитесь подтверждения применения в панели. При ошибке выполните:

```sh
sudo journalctl -u trident-agent -u trident-caddy -u trident-mita -u trident-xray -n 100 --no-pager
```

**Для NaiveProxy обязателен настоящий домен**, направленный на VPS, и доверенный TLS-сертификат. Убедитесь, что A/AAAA указывают на этот сервер, TCP 80 доступен для ACME, а протокольные порты открыты в firewall VPS и провайдера. Один IP вместо домена не завершает настройку. REALITY SNI — отдельный доступный с VPS сайт с TLS 1.3 и h2. Агент проверяет эту цель перед применением. Xray слушает IPv4 и IPv6 на одном порту; при наличии AAAA IPv6 VPS также должен быть доступен извне.

### Импорт в клиенты

| Файл | Назначение |
|---|---|
| naive.txt | Ссылка naive+https для приложения с поддержкой NaiveProxy |
| mieru.txt | Официальная текстовая ссылка mierus |
| vless.txt | VLESS URI, XHTTP + REALITY, mode=auto, flow пустой |
| naive.json | Нативный CLI naive |
| mieru.json | Нативный CLI mieru 3.37.0 |
| vless.json | Нативный Xray 26.3.27 |

Поддержка одной VLESS-ссылки не означает поддержку XHTTP в приложении. Нативный JSON каждого движка нельзя автоматически считать конфигом sing-box, Mihomo или любого мобильного клиента. Команды запуска находятся в README.txt комплекта.

## Ограничения v0.1

- Один сервер, один администратор; нет биллинга, общей квоты трафика, ролей и ограничения числа устройств.
- Нет обещаний совместимости с любым мобильным приложением: ссылки импорта и нативные JSON требуют поддержки протоколов выбранным клиентом. QR и автоматическая подписка для конкретных клиентов — следующий этап.
- mieru выдаётся как нативный JSON и официальная текстовая ссылка `mierus://`. Формат `mieru://` с protobuf здесь самостоятельно не реализуется.
- QUIC выключен по умолчанию, включение должно быть проверено отдельно. Полный набор возможностей протоколов в панель не вынесен.
- Полные перезапуски движков; горячее добавление пользователей через Xray gRPC / Caddy API / mita reload — следующая оптимизация после реального стенда.
- Нет собственных метрик трафика и общего гигабайтного лимита; интерфейс не подставляет выдуманные показатели.
- NaiveProxy/Caddy и backend сейчас запускаются под общим ограниченным системным пользователем. Root-агент имеет фиксированный набор команд и работает с root-owned исходниками/каталогом. Дальнейшее разделение служебных пользователей — этап усиления изоляции.

## Структура

```text
src/domain.mjs       валидация, ключи, порты, сроки
src/store.mjs        SQLite, шифрование, пользователи, сессии
src/configs.mjs      генераторы клиентов/серверов, ZIP
src/server.mjs       HTTP API и статика
src/agent.mjs        Linux/systemd reconciliation и откат
public/             интерфейс без сборки
deploy/             bootstrap, обновитель, локальный установщик и systemd units
.github/workflows/  проверка установки на Ubuntu 24.04
scripts/            экспорт и резервное копирование
test/               проверка логики и HTTP-сценария
docs/               архитектура, пояснения и HTTP API
```

### Как читать код

Начните с [domain.mjs](src/domain.mjs): там ограничения портов, модель статуса и генерация ключей. Затем [configs.mjs](src/configs.mjs) показывает связь одного пользователя с тремя протоколами. [store.mjs](src/store.mjs) отвечает за сохранение, [server.mjs](src/server.mjs) — за запросы браузера, [agent.mjs](src/agent.mjs) — за применение на Linux. Подробные причины решений и договорённости между модулями вынесены в [архитектурный документ](docs/ARCHITECTURE.md).

Для примеров API используйте отдельный каталог данных. Сохранение через API сразу меняет желаемое состояние; работающий агент увидит его в следующем цикле. Перед коммитом проверяйте `git status`: в репозиторий входят исходники, документация, тесты и установщик. Каталоги данных, ключ шифрования, экспорты и клиентские комплекты должны оставаться вне Git.
